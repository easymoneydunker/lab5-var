# Теория

## Зачем нужна синхронизация

Когда в программе работает несколько потоков, они выполняются «одновременно»
(на разных ядрах или поочерёдно, когда планировщик ОС переключает их).
Если потоки обращаются к общему ресурсу (переменной, файлу, окну на экране),
то без синхронизации результат непредсказуем: один поток может начать менять данные,
а другой в этот же момент прочитает их в наполовину изменённом виде.

Синхронизация решает две задачи:

1. **Взаимное исключение** — к ресурсу в каждый момент времени имеет доступ только один поток
   (или ограниченное число потоков).
2. **Ожидание события** — поток приостанавливается, пока другой поток не сообщит,
   что что-то произошло.

## Функции ожидания и объекты ожидания

**Объект ожидания** — объект ОС, у которого есть два состояния: *сигнальное* (свободен, можно идти)
и *несигнальное* (занят, нужно ждать).

**Функция ожидания** — функция, которая останавливает поток до тех пор, пока объект
не перейдёт в сигнальное состояние (или пока не истечёт тайм-аут).
Пока поток ждёт, он не тратит процессорное время.

В WinAPI это `WaitForSingleObject` / `WaitForMultipleObjects`.
В .NET все такие объекты наследуются от класса `WaitHandle`, а функции ожидания — это:

* `handle.WaitOne()` — ждать бесконечно;
* `handle.WaitOne(1000)` — ждать не больше 1000 мс, возвращает `true`, если дождались, и `false` по тайм-ауту;
* `WaitHandle.WaitAny(new[] { a, b })` — ждать любой из нескольких объектов, возвращает индекс сработавшего.

## Почему нельзя рисовать на форме прямо из потока

Окна Windows «принадлежат» потоку, который их создал (главному потоку).
Менять элементы формы из другого потока нельзя — .NET выбросит исключение
`InvalidOperationException: Cross-thread operation not valid`.
Поэтому в Delphi использовался `Synchronize`, а в C# — `Control.Invoke`/`BeginInvoke`:
мы передаём главному потоку метод, и он сам его выполняет.

## Событие (Event)

Самый простой объект синхронизации. Имеет два состояния: *установлено* (сигнальное)
и *сброшено*.

* `Set()` — установить событие, все ждущие потоки просыпаются;
* `Reset()` — сбросить событие;
* `WaitOne()` — ждать, пока событие не будет установлено.

Бывает два вида:

* **с ручным сбросом** (`ManualResetEvent`, в Delphi `ManualReset = True`) — остаётся установленным,
  пока его явно не сбросят через `Reset()`; пропускает всех ждущих;
* **с автосбросом** (`AutoResetEvent`) — после того как пропустил один поток, сам сбрасывается.

## Мьютекс (Mutex)

**Mutex** = *mutual exclusion*, взаимное исключение. Им в каждый момент может владеть
только один поток. Особенности:

* у мьютекса есть **владелец** — поток, который его захватил. Освободить его (`ReleaseMutex`)
  может только этот же поток;
* ждать мьютекс можно **с тайм-аутом**: `WaitOne(1000)` — если за секунду не удалось захватить,
  поток продолжит работу (и сам решает, что делать дальше);
* мьютекс — объект ядра ОС, ему можно дать имя и использовать из **разных процессов**
  (`new Mutex(false, "MyName")`). Например, так делают защиту от повторного запуска программы.

## Критическая секция (Critical Section)

Похожа на мьютекс: внутрь «секции» может войти только один поток, остальные ждут у входа.
Отличия от мьютекса:

* работает только **внутри одного процесса**;
* ждёт **бесконечно**, тайм-аута нет;
* работает **быстрее** и требует меньше ресурсов: пока нет конкуренции, всё происходит
  в пользовательском режиме без обращения к ядру ОС.

В C# критическая секция — это оператор `lock`:

```csharp
lock (section)
{
    DoSomethingCritical();
}
```

Компилятор превращает его в то же самое, что было в Delphi с `try..finally`:

```csharp
Monitor.Enter(section);
try
{
    DoSomethingCritical();
}
finally
{
    Monitor.Exit(section);
}
```

`finally` гарантирует, что секция будет освобождена, даже если внутри произошло исключение.

## Семафор (Semaphore)

Семафор — это счётчик свободных «мест».

* при создании задаётся начальное и максимальное число мест: `new Semaphore(3, 10)`;
* `WaitOne()` — занять место: если счётчик > 0, он уменьшается на 1 и поток идёт дальше,
  если счётчик = 0 — поток ждёт;
* `Release()` — освободить место: счётчик увеличивается на 1, и один из ждущих потоков просыпается.

Если мьютекс пускает к ресурсу **одного**, то семафор — **не больше N** потоков одновременно.
Мьютекс можно считать семафором с одним местом (с той разницей, что у мьютекса есть владелец).

## Сравнение объектов синхронизации

| | Событие | Мьютекс | Критическая секция | Семафор |
|---|---|---|---|---|
| Сколько потоков пропускает | всех (ручной сброс) / одного (автосброс) | одного | одного | до N |
| Есть владелец | нет | да | да | нет |
| Тайм-аут ожидания | да | да | нет | да |
| Между процессами | да (если с именем) | да (если с именем) | нет | да (если с именем) |
| Скорость | средняя (объект ядра) | средняя (объект ядра) | высокая | средняя (объект ядра) |
| Класс в .NET | `ManualResetEvent`, `AutoResetEvent` | `Mutex` | `lock` / `Monitor` | `Semaphore`, `SemaphoreSlim` |

## Освобождение объектов синхронизации

Объекты синхронизации — это ресурсы ОС, их нужно освобождать:

* критическую секцию — обязательно покидать (`lock` делает это сам);
* мьютекс — освобождать `ReleaseMutex()` тем же потоком, который захватил (в `finally`);
* семафор — вызывать `Release()` после работы (тоже в `finally`);
* сами объекты `Mutex`, `Semaphore`, `ManualResetEvent` после использования закрываются через `Dispose()`
  (аналог `Free` / `CloseHandle` в Delphi).

# Общая часть: класс `MoveThread`

Все потоки в работе наследуются от `MoveThread`. Он сделан похожим на `TThread` из Delphi,
чтобы код заданий был максимально близок к методичке.

```csharp
public abstract class MoveThread
{
    protected readonly PictureBox Box;
    protected volatile bool Terminated;
    protected readonly ManualResetEvent StopEvent = new ManualResetEvent(false);

    private readonly Thread thread;
    private readonly ManualResetEvent running = new ManualResetEvent(true);
    ...
}
```

* `Box` — `PictureBox`, в котором рисует поток (аналог `FBox: TPaintBox`).
* `Terminated` — флаг «пора завершаться». `volatile` нужен, чтобы поток всегда видел
  актуальное значение, а не закэшированное.
* `StopEvent` — событие, которое устанавливается при завершении. Через него можно «разбудить»
  поток, который чего-то ждёт.
* `running` — «шлагбаум» для паузы. Пока событие установлено, поток работает;
  `Reset()` — поток остановится на ближайшем шаге.

Методы:

| Метод | Что делает |
|---|---|
| `Start()` | Запускает поток (`thread.Start()`) |
| `Priority` | Приоритет потока. Изначально `Lowest`, как `tpLowest` в Delphi |
| `Suspend()` | Пауза: `running.Reset()` |
| `Resume()` | Продолжить: `running.Set()` |
| `Suspended` | `true`, если на паузе |
| `Terminate()` | Ставит `Terminated = true`, устанавливает `StopEvent` и открывает шлагбаум |
| `WaitFor()` | Ждёт завершения потока (`thread.Join()`) |
| `Execute()` | Абстрактный метод — тело потока, переопределяется в каждом задании |
| `Synchronize(action)` | Выполняет `action` в главном потоке |

### Почему не `Thread.Suspend()`

В .NET методы `Thread.Suspend()` и `Thread.Resume()` объявлены устаревшими, а в .NET Core/.NET 5+
вообще выбрасывают исключение. Причина — их опасность: поток можно остановить в момент,
когда он держит какую-нибудь блокировку, и тогда вся программа зависнет. Поэтому пауза
сделана честно: поток сам проверяет шлагбаум `running.WaitOne()` перед каждым шагом.

### Как устроен `Synchronize`

```csharp
protected void Synchronize(Action action)
{
    running.WaitOne();
    if (Terminated)
        return;

    IAsyncResult result = Box.BeginInvoke(action);
    WaitHandle.WaitAny(new WaitHandle[] { result.AsyncWaitHandle, StopEvent });
    Thread.Sleep(5);
}
```

1. `running.WaitOne()` — если поток на паузе, он здесь останавливается.
2. Если поток надо завершить — сразу выходим.
3. `BeginInvoke` отправляет метод `action` в главный поток.
4. `WaitAny` ждёт, пока главный поток выполнит метод (как `Synchronize` в Delphi — поток
   стоит, пока не отрисуется кадр). Но если пришёл сигнал завершения (`StopEvent`), ждать
   перестаём. Это нужно, чтобы не было взаимной блокировки: главный поток в `WaitFor()` ждёт
   поток, а поток ждёт главный поток.
5. `Thread.Sleep(5)` — небольшая пауза, чтобы машинки ехали с нормальной скоростью,
   а не пролетали форму за долю секунды.

### Кнопки Start / Finish

Во всех заданиях кнопки работают одинаково (как в коде из задания 5.2.4):

* **Start** — первый раз создаёт и запускает потоки, после паузы — продолжает их (`Resume`).
* **Finish** — первое нажатие ставит потоки на паузу (`Suspend`),
  повторное нажатие (когда уже на паузе) завершает их: `Terminate` + `WaitFor` и освобождает объекты.

При закрытии формы потоки тоже корректно завершаются (обработчик `FormClosing`).

# Задание 5.2.1. Синхронизация потоков с помощью критической секции

**Условие.** Два автомобиля движутся в одном компоненте. Нужно не допустить, чтобы они
использовали компонент одновременно.

**Форма** (`CriticalForm`): `PictureBox` сверху, два `TrackBar` для изменения приоритета потоков,
кнопки Start и Finish.

### Поток `CriticalThread`

```csharp
private readonly Bitmap b0;
private readonly Bitmap b1;
private readonly object section;

public int X;
public int Y;
public Bitmap Picture;
```

* `b0` — картинка машины, едущей вправо, `b1` — влево (в Delphi тоже `b0`, `b1`).
* `section` — объект критической секции, общий для обоих потоков (передаётся из формы).
* `X`, `Y` — координаты машины (в Delphi — `i`), `Picture` — что сейчас рисовать.

Конструктор ставит машину за левый край (`X = -b0.Width`) и по центру по вертикали.

Главный метод:

```csharp
protected override void Execute()
{
    while (!Terminated)
    {
        lock (section)
        {
            while (!Terminated && X <= Box.Width)
                Synchronize(DoVisualSwap);
        }
        Thread.Sleep(100);

        lock (section)
        {
            while (!Terminated && X >= -b0.Width)
                Synchronize(DoVisual);
        }
        Thread.Sleep(100);
    }
}
```

Разбор:

1. `lock (section)` — поток входит в критическую секцию (`c.Enter` в Delphi). Если другая машина
   уже внутри, поток **останавливается и ждёт**, пока она не выйдет.
2. Внутри машина едет вправо, пока не скроется за правым краем. Каждый шаг рисуется через
   `Synchronize(DoVisualSwap)`.
3. Выход из блока `lock` — освобождение секции (`c.Leave`). Теперь может войти вторая машина.
4. `Thread.Sleep(100)` — машина «разворачивается». Это нужно, чтобы второй поток успел захватить
   секцию. Без паузы первый поток мог бы сразу же снова захватить только что освобождённую секцию,
   и вторая машина ждала бы очень долго.
5. Второй блок `lock` — то же самое, но движение влево.

Методы рисования выполняются в главном потоке:

```csharp
private void DoVisualSwap()
{
    Picture = b0;
    X += 2;
    Box.Invalidate();
}
```

`Box.Invalidate()` просит перерисовать `PictureBox`. Сама отрисовка происходит
в обработчике `pictureBox1_Paint` формы: там рисуются обе машины по их координатам.
`PictureBox` по умолчанию использует двойную буферизацию, поэтому картинка не мерцает.

### Форма `CriticalForm`

```csharp
private readonly object section = new object();
```

Это и есть критическая секция (аналог `c := TCriticalSection.Create`). В C# в качестве
«замка» для `lock` подходит любой объект ссылочного типа.

Картинки `taxi00`, `taxi01` (жёлтое такси) и `rtaxi00`, `rtaxi01` (красная машина) создаются
через `Pictures.Car(...)` — вместо загрузки из файлов.

* `buttonStart_Click` — создаёт два потока (такси и красную машину), передаёт им одну
  и ту же секцию и `pictureBox1`, запускает, ставит приоритеты из ползунков.
* `trackBar1_Scroll` / `trackBar2_Scroll` — меняют приоритет потока. Значение ползунка 0..4
  соответствует `ThreadPriority.Lowest .. Highest`.
* `StopThreads()` — `Terminate` обоим потокам, затем `WaitFor` обоим. Потоки выходят из
  блоков `lock`, и секция освобождается автоматически.

### Что наблюдаем

На экране всегда едет только **одна** машина. Такси проехало вправо — освободило секцию —
поехала красная машина. Красная доехала — поехало такси обратно и т.д.
Если одну машину поставить на паузу, когда она в секции, вторая так и будет ждать —
критическая секция ждёт бесконечно.

Приоритеты влияют на то, какой поток чаще получает процессор. Так как машины всё равно
едут по очереди, а большую часть времени потоки спят, разница на современном многоядерном
компьютере почти незаметна — заметнее она при сильной загрузке процессора.

# Задание 5.2.2. Синхронизация потоков с помощью мьютекса

**Условие.** Две машины движутся в одном компоненте. Вторая машина должна появляться
только через определённый интервал времени после первой.

**Форма** (`MutexForm`): `PictureBox`, `NumericUpDown` (аналог `SpinEdit`) для времени,
кнопки Start и Finish, `Timer`.

### Форма

```csharp
public readonly Mutex m = new Mutex(false);
public volatile int time;
```

* `m` — мьютекс (`m := TMutex.Create('mutex')`). `false` — изначально никому не принадлежит.
* `time` — тайм-аут ожидания мьютекса в мс, берётся из `numericUpDown1`
  (обработчик `numericUpDown1_ValueChanged`).

Машины едут по двум полосам (`Y = 10` и `Y = 60`), чтобы было хорошо видно отставание.

`timer1_Tick` (каждые 500 мс) «будит» оба потока методом `Wake()` — это аналог того,
что в Delphi поток делал `Suspend`, а таймер его возобновлял.

### Поток `MutexThread`

```csharp
protected override void Execute()
{
    while (!Terminated)
    {
        bool owned = WaitHandle.WaitAny(new WaitHandle[] { form.m, StopEvent }, form.time) == 0;
        try
        {
            while (!Terminated && X <= Box.Width)
                Synchronize(DoVisualSwap);
        }
        finally
        {
            if (owned)
                form.m.ReleaseMutex();
        }
        WaitForTimer();

        ...то же самое для движения влево...
    }
}
```

Разбор:

1. `WaitAny(new[] { form.m, StopEvent }, form.time)` — попытка захватить мьютекс в течение
   `time` миллисекунд (аналог `m.Get(time)`). Возвращает:
   * `0` — мьютекс захвачен, `owned = true`;
   * `1` — пришёл сигнал завершения;
   * `WaitHandle.WaitTimeout` — время вышло, мьютекс так и не освободился.

   Ожидание вместе со `StopEvent` нужно только для того, чтобы при нажатии Finish поток
   не ждал до конца тайм-аута. По смыслу это обычный `m.WaitOne(time)`.
2. **Важно:** если время вышло, поток всё равно едет! Именно так работает код из методички —
   результат `Get` там не проверяется. Получается, что вторая машина ждёт первую не больше
   `time` мс, а потом трогается следом.
3. В `finally` мьютекс освобождается, **только если он был захвачен** (`owned`).
   В .NET освобождать чужой или не захваченный мьютекс нельзя — будет исключение
   `ApplicationException`. Мьютекс помнит владельца.
4. `WaitForTimer()` — аналог `Suspend` из методички: поток засыпает, пока таймер его не разбудит.

```csharp
private void WaitForTimer()
{
    wake.Reset();
    WaitHandle.WaitAny(new WaitHandle[] { wake, StopEvent });
}
```

`wake` — `AutoResetEvent`. Сначала сбрасываем его, чтобы старый «тик» таймера не засчитался
(в Delphi `Resume` для неприостановленного потока тоже ничего не делает), потом ждём.

### Что наблюдаем

* Одна машина захватила мьютекс и поехала. Вторая ждёт `time` мс и трогается следом —
  с отставанием. Чем больше время, тем больше расстояние между машинами.
* Если поставить время больше, чем машина едет через всю форму (несколько секунд),
  вторая машина дождётся освобождения мьютекса — машины едут строго по очереди, как с критической секцией.
* Если поставить 0 — машины едут почти вместе: мьютекс фактически не мешает.

Это и есть главное отличие мьютекса от критической секции: **ожидание с тайм-аутом**.

# Задание 5.2.3. Синхронизация потоков с помощью события

**Условие.** Машина перевозит пассажиров. Нельзя ездить без пассажира. Пассажиры появляются
случайно: через каждый интервал таймера с заданной вероятностью.

**Форма** (`EventForm`): `PictureBox`, два `NumericUpDown` (интервал таймера и вероятность в %),
надпись с количеством ожидающих, кнопки Start и Finish, `Timer`.

### Поток `EventThread`

```csharp
private readonly ManualResetEvent e = new ManualResetEvent(false);
private int count;
```

* `e` — событие «появился пассажир», с ручным сбросом, изначально сброшено
  (`TEvent.Create(nil, True, False, 'e')`).
* `count` — сколько пассажиров ждёт на остановке.

`b0` — пустое такси (едет вправо к остановке), `b1` — такси с пассажиром (едет влево).

```csharp
public void AddPassenger()
{
    Interlocked.Increment(ref count);
    e.Set();
}
```

Этот метод вызывает таймер формы: пассажиров становится на одного больше и событие
устанавливается — ждущий поток просыпается. `Interlocked.Increment` увеличивает счётчик
атомарно, потому что с `count` работают два потока (главный и поток машины).

```csharp
protected override void Execute()
{
    while (!Terminated)
    {
        while (!Terminated && X <= Box.Width - b0.Width - 50)
            Synchronize(DoVisualSwap);

        WaitPassenger();

        while (!Terminated && X >= -b0.Width)
            Synchronize(DoVisual);
    }
    e.Dispose();
}
```

1. Такси едет вправо к остановке.
2. `WaitPassenger()` — ждёт пассажира.
3. Едет влево уже с пассажиром, скрывается за левым краем и возвращается.
4. После выхода из цикла событие освобождается (`e.Free` в Delphi).

```csharp
private void WaitPassenger()
{
    e.Reset();
    while (!Terminated && Count <= 0)
    {
        WaitHandle.WaitAny(new WaitHandle[] { e, StopEvent });
        e.Reset();
    }

    if (!Terminated)
        Interlocked.Decrement(ref count);
}
```

Это то же самое, что в методичке:

```pascal
if count <= 0 then
begin
  e.ResetEvent;
  e.WaitFor(100000);
end else count := count - 1;
```

* Если на остановке есть пассажиры (`count > 0`) — сразу забираем одного (`count - 1`) и едем.
* Если нет — сбрасываем событие и **ждём**, пока таймер его не установит.

Порядок «сначала `Reset`, потом проверка `count`» важен: если сделать наоборот, таймер мог бы
добавить пассажира и установить событие *между* проверкой и сбросом — тогда сигнал потеряется,
и машина будет стоять, хотя пассажир есть. Цикл `while` нужен, чтобы после пробуждения ещё
раз убедиться, что пассажир действительно есть. В отличие от методички, после ожидания
пассажир тоже вычитается из счётчика — иначе счётчик рос бы бесконечно.

### Форма

```csharp
private void timer1_Tick(object sender, EventArgs e)
{
    if (random.NextDouble() <= (double)numericUpDown2.Value / 100)
        thread1.AddPassenger();

    labelCount.Text = "Ожидают пассажиров: " + thread1.Count;
    pictureBox1.Invalidate();
}
```

Это генератор событий из методички (`if random <= SpinEdit1.Value/100 then ...`).
`random.NextDouble()` даёт случайное число от 0 до 1. Если оно меньше вероятности — появляется пассажир.

`numericUpDown1_ValueChanged` меняет интервал таймера. В `pictureBox1_Paint` рисуется остановка
(столбик с табличкой у правого края), человечки на ней и сама машина.

### Что наблюдаем

* При высокой вероятности и маленьком интервале пассажиров больше, чем машина успевает
  перевезти, — очередь растёт, машина ездит без остановок.
* При низкой вероятности машина подолгу стоит у остановки — поток заблокирован
  на событии и **не тратит процессорное время**.
* При вероятности 0 машина доедет до остановки и будет стоять бесконечно.

# Задание 5.2.4. Синхронизация потоков с помощью семафора

**Условие.** Есть 10 потоков (капель). Одновременно могут выполняться только заданное
количество, остальные ждут. Кнопка Sleep приостанавливает все потоки функцией `Sleep`.

**Форма** (`SemaphoreForm`): два `PictureBox` (сверху полоска с облаками, под ней поле для капель),
два `NumericUpDown` (максимальное количество капель и время приостановки), кнопки Start, Finish, Sleep.

### Поток `DropThread`

```csharp
public DropThread(int num, Semaphore h, PictureBox c, PictureBox d) : base(c)
{
    X = 32 * (2 * num - 1) - 16;
    h0 = h;
    dBox = d;
}
```

* `num` — номер капли 1..10. По нему вычисляется горизонтальная позиция (та же формула,
  что в методичке: `numb := 32*(2*numb-1)-16`), то есть каждая капля в своём столбце.
* `h0` — семафор (в Delphi — `THandle`).
* `c` — поле для капель (`FBox`), `d` — полоска с облаками (`DBox`).

Поля: `I` — вертикальная координата капли, `Up` — летит вверх или вниз,
`Active` — капля сейчас «работает» (захватила семафор), `Frame` — кадр анимации ожидания.

```csharp
protected override void Execute()
{
    while (!Terminated)
    {
        while (!h0.WaitOne(200))
        {
            if (Terminated)
                return;
            Synchronize(DoWait);
        }

        try
        {
            Synchronize(DoStart);
            while (!Terminated && I > 0)
                Synchronize(DoMoveUp);
            while (!Terminated && I < Box.Height - DropHeight)
                Synchronize(DoMoveDown);
            Synchronize(DoStop);
        }
        finally
        {
            h0.Release();
        }
    }
}
```

Разбор:

1. `h0.WaitOne(200)` — попытка занять место в семафоре, ждём 200 мс
   (`WaitForSingleObject(h0, 200)`). Если мест нет — возвращается `false`, поток рисует кадр
   анимации ожидания (`DoWait` — облако мигает серым) и пробует снова.
2. Как только место освободилось — капля становится активной (`DoStart`, облако синеет),
   поднимается снизу вверх (`DoMoveUp`), затем падает вниз (`DoMoveDown`).
3. `h0.Release()` — освобождаем место в семафоре (`ReleaseSemaphore(h0, 1, nil)`), и одна
   из ждущих капель может стартовать. `Release` стоит в `finally`, чтобы место освободилось
   даже при завершении потока посреди полёта.

### Форма

```csharp
private readonly DropThread[] thread = new DropThread[10];
private Semaphore fsemaphore;
```

`buttonStart_Click`:

```csharp
int maxCount = (int)numericUpDown1.Value;
fsemaphore = new Semaphore(maxCount, 10);
for (int i = 0; i < 10; i++)
{
    thread[i] = new DropThread(i + 1, fsemaphore, pictureBox1, pictureBox2);
    thread[i].Start();
}
```

`new Semaphore(maxCount, 10)` — то же, что `CreateSemaphore(nil, max_count, 10, nil)`:
сначала свободно `maxCount` мест, максимум 10. Создаются и запускаются 10 потоков.
Если потоки на паузе — Start их просто возобновляет.

`buttonFinish_Click` — пауза / завершение. При завершении после `WaitFor` всех потоков
семафор закрывается: `fsemaphore.Dispose()` (`CloseHandle(fsemaphore)` в Delphi).

```csharp
private void buttonSleep_Click(object sender, EventArgs e)
{
    Thread.Sleep((int)numericUpDown2.Value);
}
```

`Sleep` вызывается **в главном потоке**. Главный поток засыпает и не обрабатывает сообщения.
Все потоки капель на следующем шаге вызывают `Synchronize` и ждут, пока главный поток
выполнит их метод отрисовки, — поэтому останавливаются все потоки разом.
По окончании `Sleep` движение продолжается.

`pictureBox2_Paint` рисует облака: синее — капля активна, мигающее серое — капля ждёт семафор.
`pictureBox1_Paint` рисует летящие капли.

### Что наблюдаем

* Одновременно летит ровно столько капель, сколько задано в «Максимальное количество капель».
  Остальные облака мигают серым — эти потоки ждут на семафоре.
* Как только одна капля закончила полёт и вызвала `Release`, сразу стартует другая.
* При максимуме 10 летят все капли сразу; при 1 — по одной (семафор работает как мьютекс).
* Изменение максимума действует после перезапуска (Finish → Finish → Start), потому что
  начальное число мест задаётся при создании семафора.
* Кнопка Sleep замораживает и форму, и все капли на заданное время.

# Выводы

1. **Критическая секция** (`lock`) — самый быстрый и простой способ не пустить два потока
   в один участок кода. Ждёт бесконечно, работает только внутри процесса.
2. **Мьютекс** делает то же самое, но позволяет ждать с тайм-аутом и работать между
   процессами. У мьютекса есть владелец — освобождает его тот же поток, что захватил.
3. **Событие** не защищает ресурс, а служит для оповещения: один поток ждёт, другой
   сообщает «можно». Пока поток ждёт событие, он не нагружает процессор.
4. **Семафор** ограничивает число потоков, одновременно работающих с ресурсом.
5. Все объекты синхронизации нужно освобождать (`ReleaseMutex`, `Release`, выход из `lock`,
   `Dispose`), лучше всего в блоке `finally`.
6. Элементы формы можно менять только из главного потока — для этого служит
   `Synchronize` в Delphi и `Invoke`/`BeginInvoke` в C#.
